## Standards

### 判断性发现（Fowler 基线）

1. **Duplicated Code / Repeated Switches（最强）** — `img_proxy.ts:360-371` 与 `text_proxy.ts:106-117` 是同一份 `ProxyFetchResult` → `{status,message}` 的 if 级联，本次新增 `resolution_failed` 分支迫使两处同改（Shotgun Surgery 前兆）。text_proxy 已从 img_proxy 导入多个共享函数，抽一个 `proxyFailureResponse(kind)` 符合既有模式。
2. **Duplicated Code / Primitive Obsession** — DNS 记录类型魔术数 `1/28` 在 `img_proxy.ts:188` 与 `tests/img_proxy.test.ts`（`netAnswer` 内）各写一份；宜导出 `DOH_TYPE = { A: 1, AAAA: 28 }` 供测试复用。同时 `queryDoh` 末尾 `as string`（191 行）可用类型谓词收窄，避免断言。
3. **文档漂移（近硬性，仍判判断性）** — `img_proxy.ts:133-136` 自述“任何新增规则都只改 validateTargetUrl”，本次规则落在异步 `resolveAndCheckTarget`；实质要求（每一跳都校验）已满足，但该注释未更新为“同步 URL 层 + 异步解析层”两层契约，后续维护者易只改一处。
4. **性能/成本** — 每跳固定 2 次 DoH、无按主机 memo（`resolveAndCheckTarget` 无缓存），≤6 跳即 ≤12 次外部查询，全部计入同一 10s 预算（`FETCH_TIMEOUT_MS`），会拉高图片代理延迟与外部依赖；按请求去重 distinct host 即可。
5. **语义混淆（Mysterious Name 轻度）** — 父 `signal` 因总超时中止时同样走 `queryDoh` 的 catch → `'failed'`，对外报“目标域名解析失败”（`img_proxy.ts:364`/`text_proxy.ts:110`），与“总超时/上游失败”不可区分，信息误导。
6. **测试覆盖缺口** — 新文件只覆盖 `fetchWithValidatedRedirects` 接缝；`text_proxy.ts:109-111` 新增分支（CORS + 502）零覆盖，重定向跳用例也未断言是 URL 校验还是 DoH 拦截。
7. **README 表格不对称** — 图片行/安全条目已写“解析后 IP 复核”，文字行（174 行）仍不体现共享的 SSRF 复核（旧有不对称，本次未趁改而补齐）。
8. **一致性小项** — DoH 的 `fetch`（`img_proxy.ts:181`）未设 `redirect: 'manual'`，与该文件自述“重定向不自动跟随”原则不一致；端点硬编码可接受，不必参数化。

## Spec

**已核验**：`npm run typecheck`、`npm test` 本地均通过（19 测试）；AC「解析到受限段即拒」「mapped 字面量不回退」「失败/超时 fail-closed」在代码与测试中均有落实（`resolveAndCheckTarget` fail-closed，TOCTOU 注释齐备）。

### (a) spec 要求了、缺失或半成品

1. **AC「站内正常外链图片/文字代理不受影响」既无防护也无验证**：每次 cache-miss 都现场双查 DoH（`img_proxy.ts:208-214`，≤3s）、结果不缓存、DoH 端点限流/故障即整体 502；且无 A 记录（仅 CNAME）时 `ips.length===0` → `resolution_failed`。新测试全部把 DoH 打桩，无 handler 级端到端用例覆盖「正常外链仍可代理」，该 AC 实际未被证明。
2. **Key interfaces 未落实**：「代理目标 URL 校验函数（两通道共用）：新增『解析后 IP 复核』步骤」——复核实际放在新的异步 `resolveAndCheckTarget`，`validateTargetUrl` 仍是同步且不含复核（`img_proxy.ts:137-159`）；单独调用该共用校验函数的路径会漏检，且 `img_proxy.ts:228` 注释「每一跳都复用 validateTargetUrl」已与事实不符。
3. **「两通道行为一致」仅共享代码层成立**：`worker/tests/` 只有 `img_proxy.test.ts`，text 通道 502 分支与 `corsify` 包裹零测试。
4. **受限段未穷尽**：测试覆盖 AC1 所列全部段（+100.64/0.0.0.0），但 DoH 返回的 NAT64/6to4/映射压缩形式（`64:ff9b::7f00:1`、`::ffff:7f00:1`、`2002:...`）不拦——「等任一」留有 SSRF 通路。

### (b) 范围蔓延（diff 出现、spec 未要求）

- 测试基建：`deploy.yml` 新增 Test 步骤、vitest 依赖、`tsconfig.test.json`，并导致 `package-lock.json` 全量重排（+2244/−375，重解全部传递依赖，引入 `node ^22.20` 引擎要求）；ticket 未要求，作为 AC 证据可接受，但 lockfile 面与「`npm install` 非 `ci`」值得单独收敛。
- README 4 处文档更新，合理。

### (c) 实现问题

1. 文案错误：首跳（非重定向）因区块链被拒时返回 403「重定向目标被禁止代理」（`img_proxy.ts:360-362`、`text_proxy.ts:106-108`）。
2. `isIpLiteralHost` 用 `includes(':')` / `/^[0-9.]+$/` 粗判（`img_proxy.ts:173-176`），`1.2.3.4.5`、`999.1.1.1` 被当字面量直接放行且跳过 DNS 复核。
3. `AbortSignal.any` 用法在 compat date 2024-09-23 的 workerd 上可用性未经仓库/CI 验证；若缺失将抛异常→500（仍 fail-closed）——建议加真实 runtime 冒烟或降级为单信号。
4. 每跳重查 DoH、命中率无缓存，最多 6 跳 ×2 查询，放大限流与延迟风险。

## 复核备注（非技能输出）

**复审后处置**（提交 `38c3cf8`，均已本地验证）：

1. 标准 (5) / Spec (c)1：`blocked` 文案统一为「目标地址被禁止代理」；`resolution_failed` 文案改为「目标域名解析失败或超时，已拒绝代理」（两通道同步）。

4. 标准 (7)：README text-proxy 行补齐共用 SSRF（含解析后复核）校验描述。
