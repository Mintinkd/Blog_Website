## Spec

**(a) 要求缺失或只做了一半**：

1. Spec：「未知用户名与已知用户名的响应耗用时序差仍在可接受范围」——只落了常量，没有测量、预算或理由。本地 Node 实测：1 000 次 ≈ 0.4 ms，100 000 次 ≈ 23.7 ms，约 55×；新测试把该差距钉为预期输出，而不是断言响应耗时接近，#17 的防枚举属性被静默回退。
2. Spec Summary：「攻击者可提交超大字符串」——`request.json()`（`auth_handler.ts:165`）仍先解析并分配完整请求体，再在 `:178` 做长度检查。KDF 早退（AC）已满足，请求体解析仍未设界（无 `Content-Length` 守卫），属残项。
3. Spec：「边界值单测：上限值本身通过、上限+1 被拒」——登录侧完整（`auth_login.test.ts:88-133`）；另外三条被补上上限的路径只有 201 拒绝用例，没有 200 通过用例。

**(b) 未要求的行为（scope creep）**：

- Spec Key interfaces 只点名「登录 handler 入参校验」与「假验证函数」，diff 另把上限挂到建号 / 自助改密 / 管理员重置（`auth_handler.ts:400-409, 477-483, 523-529`）并改 README 四行。Spec 原话「与建号/改密口径一致，如 200 字符」，但修复前三路本无上限（只有 `MIN_PASSWORD_LENGTH = 8` 与弱口令名单），该前提不成立。
- **判断：合理保留**——要让 Spec 声称的「口径一致」成立，必须同时收口这三条写入路径，且它们同样存在无界输入哈希。代价是站点级新策略：存量 >200 字符口令现在登录即 400，只能经管理员重置为 ≤200 恢复；README 登录段已记录该口径。

**(c) 看起来实现了但实际有问题**：

1. 1000 次迭代取自审查报告示例，但 Spec 第三条「假验证的意义是抹平差异，不是放大攻击面」未被证明；约 24 ms 的 KDF 与约 0.4 ms 哑运算可被远程区分，账号枚举面重新打开。要么记录接受该差值并修正 #17 的表述，要么在明确预算内用固定成本 / 补偿延迟。
2. 陈旧断言（同 Standards 硬违规）：`auth_handler.ts:191`、`:341` 仍称「同代价」「抹平（#17 AC4）」，与实现不符。

**核对通过**：T6（#48）仍 OPEN，diff 未加任何登录限流，符合「T6 完成前不要在登录接口挂限流」；AC1（超限 400 且不进 KDF）、AC2（假验证常量与配置解耦）、AC3（边界）、AC4（门禁）均有对应用例且全绿。
